# Apollo application-library audit

> Classification scope: read this audit with the [ecosystem plan](../application-library-ecosystem.md) and [boundary review](boundary-review.md). A generic API or core gap below describes the inspected current interfaces/composition. It does not require product behavior in the shell or a mandatory dependency on bundled Catalog, Launch, NVHTTP or transport. Library, protocol, networking and packet delivery implementations are intended to remain independently replaceable.

Scope: source/documentation comparison, 2026-10-31. Amaterasu checkout `f8aa56337288632df64db1cca807dd3b0cd6beaa`. Apollo references below are its mutable `master` as retrieved, except the versioned wiki and release; exact master commit could not be established, so recheck against a pinned commit before implementation. This is requirements evidence, not a runtime or parity certification. Native providers are trusted code, not sandboxed.

Offer an authorized lookup/launch by external identity and current app identity only if needed. Test duplicate names, same UUID across providers, stale IDs and reimport. |
| Per-app/per-client profiles: Apollo exposes app/client UUID/name and requested stream attributes to commands in [process.cpp](https://github.com/ClassicOldSong/Apollo/blob/master/src/process.cpp); [Profile Manager](https://github.com/ClassicOldSong/Apollo/releases/tag/v0.3.5-alpha.5) documents separate per-app/per-client file settings, saves and mods. Carry immutable context consistently through start, recovery and lifecycle without treating display name or untrusted uniqueid as authority. Test two paired clients, same app, reconnect and re-pair, context isolation, and provider restart. Per-app/client display identity requires separate display-owner integration. |
| Per-client connect/disconnect commands, with per-app opt-out; intended for suspend/resume ([versioned Apollo wiki](https://github.com/ClassicOldSong/Apollo/wiki/Client-Commands/1c8037a201aa7a523b842bfa1f8d72984535a5df)); client configuration persists command lists, permissions and settings ([nvhttp.cpp](https://github.com/ClassicOldSong/Apollo/blob/master/src/nvhttp.cpp), [confighttp.cpp](https://github.com/ClassicOldSong/Apollo/blob/master/src/confighttp.cpp)). | **Partial core / generic lifecycle gap:** app prep/undo and exclusion of global prep exist (`modules/catalog/src/model.rs:66`), and executable launch passes preparation (`modules/launch/src/workflow.rs:118`). Existing session-lifecycle capabilities require separate qualification for this exact policy. | Provide a client-scoped connection lifecycle hook with authenticated app/client correlation and explicit app opt-out; define behavior on disconnect, resume, terminal stop, failures, retries and concurrent clients. Test one connect/disconnect per transition, resumption, partial prepare failure, rollback, fencing and no leakage across app/client pairs. Do not claim generic lifecycle callbacks exist today. |
| Preparation do/undo, elevation, detached commands, cwd, managed process exit behavior; [Apollo app examples](https://github.com/ClassicOldSong/Apollo/blob/master/docs/app_examples.md) explain detached Steam and undo. | **Core partial / provider implementable:** app prep with do/undo and elevation (`modules/catalog/src/model.rs:83`); executable detached, auto-detach, wait-all, timeout (`modules/catalog/src/model.rs:933`), passed to process owner (`modules/launch/src/workflow.rs:118`). Generic provider target does not expose executable detached fields, so provider may implement its own semantics subject to retirement contract. | Preserve ordered prep and reverse undo across failure/stop; support detached launcher whose initial process exits and a desktop/no-managed-process launch. Specify what a provider can prove stopped and fail closed on unknown outcome; test delayed start, lost reply, restart, do failure and detached process/URI, including cleanup evidence. Full Apollo-equivalent process and privilege semantics remain unverified. |
| App cover image and user-controlled app order; Apollo reorder accepts UUIDs and appends unmentioned entries ([confighttp.cpp](https://github.com/ClassicOldSong/Apollo/blob/master/src/confighttp.cpp)); compatibility differs by client ([release](https://github.com/ClassicOldSong/Apollo/releases/tag/v0.3.5-alpha.5)). | **Public generic-API and core presentation gaps:** discovery exposes provider artwork ref (`crates/module-sdk/src/application_library.rs:267`) and adapter artwork callback (`provider_adapter.rs:74`), but catalog artwork enum/routes are restricted to Steam/Lutris/Playnite (`modules/catalog/src/model.rs:94`, `modules/library/src/artwork.rs:10`; also `docs/application-library-provider-configuration.md:168`). Add a stable ordered projection independent of identifier and pagination; support an explicit compatible legacy encoding only when negotiated, test reorder/add/remove and client capabilities. |
| Apollo has paired-client permissions and list/launch controls ([client update source](https://github.com/ClassicOldSong/Apollo/blob/master/src/confighttp.cpp)); client commands can be disabled per app. Evidence reviewed does **not** establish an Apollo per-app access-control list. | **Partial core, visibility unknown:** NVHTTP checks authenticated TLS, list and launch flags (`modules/nvhttp/src/wire.rs:29`, `:357`); generic discovery is restricted by component initiator, not individual paired client (`modules/library/src/discovery.rs:105`). No public per-client context in generic discovery. | Preserve list vs launch checks; if per-client visibility is a product requirement, enforce the same authenticated policy at listing, artwork, resolve and launch, including direct-ID attempts, reconnect/revocation and race tests. Do not infer an Apollo per-app ACL from general client permissions. |

Additional boundaries: Apollo's [remote input special mode](https://github.com/ClassicOldSong/Apollo/discussions/1445) is reported by its maintainer as custom logic rather than a real app; do not force its identity into a normal catalog record without a separate protocol design. Source review did not establish all Apollo visibility rules, ordering wire representation, or recovery under actual process crashes. Validate chosen requirements against a pinned upstream revision and real clients/providers before claiming parity. No implementation, build, host operation, or runtime behavior was tested in this audit.
