# DuoStream / Duo — application-library audit

> Classification scope: read this audit with the [ecosystem plan](../application-library-ecosystem.md) and [boundary review](boundary-review.md). A generic API or core gap below describes the inspected current interfaces/composition. It does not require product behavior in the shell or a mandatory dependency on bundled Catalog, Launch, NVHTTP or transport. Library, protocol, networking and packet delivery implementations are intended to remain independently replaceable.

Audited 2026-10-31 against Amaterasu `f8aa56337288632df64db1cca807dd3b0cd6beaa`. The official [DuoStream/Duo repository](https://github.com/DuoStream/Duo) identifies Duo as Windows multiseat streaming based on TermWrap, Sunshine, Moonlight and patches; [latest release](https://github.com/DuoStream/Duo/releases/tag/v1.6.0) is v1.6.0. The public repository root contains README and wiki images, not the implementation. Findings are documentation/source comparisons, not runtime verification.

## Documented behavior and limits

- [README](https://github.com/DuoStream/Duo) says each user gets an independent desktop and that multiple Steam instances are supported. Its free tier has one additional Duo instance; supporter tier permits more. [Setup](https://github.com/DuoStream/Duo/wiki/Setup-Guide#creating-instances) assigns a local Windows user to each instance and pairs a client to the selected instance; [Settings](https://github.com/DuoStream/Duo/wiki/Settings#patch-settings) describes isolation required for concurrent Steam clients. [Known issues](https://github.com/DuoStream/Duo/wiki/Known-Issues) describes independent terminal sessions and registry-based instance configuration.
- These establish multiseat and user/session context, **not** that Duo has separate app catalogs, particular metadata, artwork, app profiles, per-app permissions, or any public library integration API. Its actual catalog storage, synchronization, API, authentication, game entitlements and cross-instance behavior remain unknown. WebUI documented for instance start/stop is not evidence of an application-library API. No reference code was copied.

## Amaterasu comparison and actionable requirements

1. **Generic context/authorization gap, conditional on a multiseat integration:** catalog owner selection today is fixed from authenticated caller/importer/export mappings, with no caller-selected owner (`modules/catalog/src/pipeline.rs:299-305,322-343,376-396`; `modules/catalog/src/protocol.rs:65`). The library list/resolve requests derive identity from broker and have no instance selector (`crates/module-sdk/src/application_library.rs:17-51`). A provider can encode a stable namespace in source IDs or use separately configured principals and catalogs, but this alone does not prove authenticated end-user/instance authorization or dynamic per-instance catalogs. If a shared process must serve different instances, define an authenticated, host-bound opaque instance/user context consistently across discovery, import, list, resolve, artwork, launch and cleanup; never trust a request-supplied owner. Accept with two isolated identities containing overlapping source IDs: reads, updates, removal, launch and artwork cannot cross scopes, including restart/revocation and stale cursors. If independently deployed per-instance hosts suffice, verify that topology first rather than imposing a global schema.
2. **Provider implementation and generic artwork gap:** provider discovery has stable ID/name and optional opaque artwork ID/revision and revision-consistent pagination (`crates/module-sdk/src/application_library.rs:242-290`); snapshot imports have bounded entries/removals and catalog validation (`:76-97`). Catalog supports name, description, tags, overrides and launch (`modules/catalog/src/model.rs:12-76`), but artwork variants are hardcoded Steam/Lutris/Playnite (`:94-102`). Documentation explicitly says generic discovery does not enable generic catalog artwork (`docs/application-library-provider-configuration.md:168-173`). An independently implemented provider can discover/import rows and own provider lifecycle when source integration is actually available; add opaque provider-routed artwork with approved route, exact revision and bounded chunk verification if an integration needs its own images. Acceptance: two providers with colliding local artwork IDs cannot read each other's image; changed revision, invalid cursor and unauthorized requester fail closed. Duo-specific artwork needs remain unknown.
3. **Core session/runtime gap, distinct from catalog schema:** lifecycle requests include operation ID, application ID, provider incarnation and ticket, but no seat/user context (`crates/module-sdk/src/application_library/provider_lifecycle.rs:17-24`); launch pipeline has one in-flight workflow (`modules/launch/src/pipeline.rs:413-421`) and builds launch workflows from app/initiator (`:816-834`). These observations do not alone prove the total number of established sessions supported. Duo-like independent simultaneous sessions need a separate end-to-end investigation and implementation spanning session identity, Windows user/process execution, paired-client routing, capture/input/audio isolation, lifecycle ownership and concurrent launch/stop. Acceptance must demonstrate two actual independently authenticated sessions and games, stopping/recovering one without affecting the other. Multiple Steam operation also requires a compatible platform integration; a catalog provider alone cannot supply it.
4. **Profiles and tooling:** per-app core overrides already exist in catalog (`modules/catalog/src/model.rs:27-76,144-170`); do not invent Duo-specific profile fields without evidence. Generic discovery projections expose only ID/name/artwork, and public catalog reads expose ID/name (`crates/module-sdk/src/application_library.rs:46-70,267-281`); richer presentation needs an independently justified, bounded versioned contract if requested by a consumer. The documented provider setup requires explicit package, grants and route configuration, and makes providers responsible for durable reconciliation and fencing (`docs/application-library-provider-configuration.md:76-81,125-189`). Adapter lifecycle enforces identity and retirement assertions (`crates/module-sdk/src/application_library/provider_lifecycle.rs:1-6,88-120`). Qualify any real provider against restart, lost response, delayed start, duplicate operation and isolated stop. Native modules are trusted code; grants route authority and do not sandbox them (`crates/module-sdk/src/application_library.rs:3-6`).

**Evidence boundary:** no Duo installation, process behavior, binary inspection, game launch or authenticated API was tested; no claim is made that Duo implements per-user libraries or that Amaterasu already offers Duo multiseat parity.
