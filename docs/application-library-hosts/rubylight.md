## Observed host contract

* [README: Every launcher, one library](https://github.com/RamazanKara/Rubylight/blob/55decb95abfe49847cfa06ed2567fb7b0d913054/README.md) and [features: Game library](https://github.com/RamazanKara/Rubylight/blob/55decb95abfe49847cfa06ed2567fb7b0d913054/docs/features.md#game-library) describe installed Steam, Epic, Battle.net, EA, Ubisoft, GOG, Microsoft Store/Xbox, Playnite and folder games, cover art, launcher switches, sync, and game and device settings. Steam sync is documented every 30 seconds and on demand; these are product behaviors, not a requirement to replicate polling or store parsing in core.
* [Native API: Library](https://github.com/RamazanKara/Rubylight/blob/55decb95abfe49847cfa06ed2567fb7b0d913054/docs/native-api.md#library) documents configured apps, a host-local stable `install_id`, optional cross-host `<source>:<store id>` `game_id`, numeric legacy `app_id`, open-ended store source, cover version, `installed` true/false/unknown, and current running flag. Microsoft covers Xbox PC and Store GDK titles, with explicit scan error and unsupported/nonlaunchable cases. Last scan is cached and refreshed in background at most every five minutes and after imports; read does not await scan. It does not establish a complete entitlement catalog or ability to install all uninstalled games. [HTTP API](https://github.com/RamazanKara/Rubylight/blob/55decb95abfe49847cfa06ed2567fb7b0d913054/docs/api.md#api-reference) lists Playnite install/uninstall actions, but do not generalize these to every launcher.
* [Native API](https://github.com/RamazanKara/Rubylight/blob/55decb95abfe49847cfa06ed2567fb7b0d913054/docs/native-api.md) requires paired certificate and device permissions, capability negotiation, read library, and owner-scoped session view; disconnect retains game, end releases session while game remains, close additionally quits game and requires host control. Client-facing session actions and the library are separate from launch/resume protocol. The feature reference describes launcher sign-in/update notices and a confirmed game switch. Client-side favorites, caching, cross-host merging and profile UI need host facts, but do not imply host-side storage for those features.

## Amaterasu assessment

| Area | Classification and evidence |
| --- | --- |
| Import and ownership | **Existing seam / provider implementation needed.** SDK batches have bounded, unique source IDs and source revision/epoch, ordered generation, staged publication and explicit finish/removal options: `/home/chasep/sources/amaterasu/crates/module-sdk/src/application_library.rs:76`, `:128`. Durable ownership is importer + source ID (`modules/catalog/src/product.rs:175`); snapshots can include removals. A real trusted independently built provider must perform discovery/import; configuration explicitly says the example is synthetic and doesn't import or launch (`docs/application-library-provider-configuration.md:3`, `:22`). Distinct stores can be namespaced inside provider source IDs, but no proof of all requested stores or cross-host canonical IDs is supplied by that fact. |
| Discovery and user selection | **Generic API gap.** Opt-in routed provider discovery supports bounded pagination (`modules/library/src/discovery.rs:23`, `:104`) and rows only id/name/optional artwork (`:44`). It lacks typed source, install/launchable state, already-added status, filter and a generic selected-item add/sync command. Provider can own scanning/scheduling; management-facing selection and synchronization semantics require an explicit shared contract if clients are to consume it. |
| Rich library and identity | **Generic API gap.** Catalog entry stores name, description, tags, Steam identity and launch configuration (`modules/catalog/src/model.rs:12`); library deliberately projects only id/name and revision (`modules/library/src/lib.rs:112`, `:136`; SDK `crates/module-sdk/src/application_library.rs:32`). It does not publish a portable store/game identity or installed/running status through this facade. Stable catalog identity must not be conflated with cross-host identity or Moonlight numeric ID. Catalog search exists (`modules/catalog/src/protocol.rs:360`), but library list rejects query-bearing cursors (`modules/library/src/lib.rs:64`). |
| Artwork | **Generic API gap.** SDK provider adapter has artwork callback (`crates/module-sdk/src/application_library/provider_adapter.rs:25`, `:74`), yet catalog `ArtworkReference` is closed to Steam/Lutris/Playnite (`modules/catalog/src/model.rs:94`) and generic discovery does not enable generic artwork routing (`docs/application-library-provider-configuration.md:168`). A discoverable opaque reference alone is not an end-to-end generic image route. |
| Application launch | **Existing seam / real provider needed.** Generic adapter has launch, lookup, recover-stop, stop, stable operation and incarnation (`crates/module-sdk/src/application_library/provider_adapter.rs:18`); contract requires deduplication and fencing (`provider_lifecycle.rs:1`). Launch owns session/preparation and retains the lease if retirement cannot be established (`docs/application-library-provider-configuration.md:175`). The provider owns actual process reconciliation, launcher requirements, and cleanup; adapters and grants do not prove effects. |
| Profiles/authorization | **Partial, further client interface unknown.** Catalog supports sparse per-app config and preparation (`modules/catalog/src/model.rs:27`, `:64`); NVHTTP checks List permission (`modules/nvhttp/src/wire/applications.rs:165`, `:231`), and a launch profile exists (`modules/nvhttp/src/launch.rs:469`). These references do not establish a rich paired-client view of effective per-device/app settings or caller-specific actions. SDK caller/initiator policies (`provider_adapter.rs:53`, `:96`) are service principals, not per-device permissions. Verify end-to-end policy propagation before claiming parity. |
| Independent session actions | **Core/session and client projection gap to verify.** Existing launch/session coordinator tracks application ownership and retirement (`modules/session-lifecycle/src/coordinator/application.rs:8`, `:128`); NVHTTP has cancel (`modules/nvhttp/src/launch.rs:1197`). These alone do not prove that a paired client can request all three Rubylight semantics (disconnect, end stream and retain game, close game) with correct owner/host-control checks. Do not weaken retirement to simulate end-session retention. |
| Events/refresh | **Partly provider-owned; client contract gap.** Snapshot revisions and pagination support polling/reconciliation; incremental snapshot batches can persist before failed finish (`crates/module-sdk/src/application_library.rs:1`). No library subscription/event API was established in the inspected facade. Rubylight documents polling session about 2 seconds, not a requirement for push; provider may rescan or observe changes itself. Do not claim absence of all system-wide events. |

## Minimal extensions and acceptance

1. Define a versioned, bounded rich library/discovery projection with stable host-local ID, opaque provider + source ID, optional namespaced portable store ID and display name, tri-state installed and launchability/reason, selected/already-added state, optional versioned cover reference, and revision. Preserve unknown for unsupported facts; distinguish multiple store copies and avoid unsafe title-based merging. Existing clients continue consuming v1; support paging with stale-revision restart and query/filter semantics without exposing paths or launch commands. Validate scans that fail or partially finish never make every game appear removed; rescans retain user edits according to explicit ownership rules.
2. Add capability-negotiated provider-agnostic image resolution using authorized provider route + opaque identity and revision, bounded chunking/content type/total size and cancellation; reject cross-provider references, changed incarnation/revision, invalid chunks and stale transfers. Verify SDK callback through the actual library facade, not a provider fixture in isolation.
3. Specify selection/add and optional install/uninstall as separately authorized, capability-advertised provider operations with idempotent operation identity, progress/error/unknown state, safe retries and reconciliation. A provider that merely discovers installed apps need not implement install or expose entitlements. Allow manual entries; preserve user choices on import/update. Do not embed launcher internals in core.
4. Publish authenticated, device-authorized rich query and session projection with per-device list/view/launch/control permissions, state/owner and permitted actions. Give clients the facts to present inherited effective settings and unavailable reasons, while keeping client favorites and multi-host merging client-owned unless independently required. Test unauthorized, other-device, revoked and unpaired cases.
5. Specify disconnect, retained-game end, close, resume, concurrent game-switch confirmation and cleanup as distinct coordinated actions. Test races, crash/restart, lost replies, incarnation change and delayed start; unknown retirement must remain unknown, and close requires a real provider stop/retirement assertion. Preserve game on end only where session and resource ownership semantics prove it safe.
6. Qualify an independently implemented provider on real Windows launcher installations and actual selected signed binaries: each supported store including Xbox/Microsoft; duplicates and manual rows; selection, rescans, uninstalled/unknown states and scan errors; cover versions; start, exit, failure and restart cleanup; device permissions and live session behavior. Unit fixtures alone establish none of those end-to-end effects.

This is source and upstream-document comparison only: no tests, hardware, installed runtime, client interoperability, store authentication or Windows process behavior were exercised. Exact Rubylight native-wire compatibility would additionally require versioned endpoint/fixture interoperability work; the generic needs above do not claim Nightjar can already use Amaterasu. Provider discovery and lifecycle do not sandbox native code: broker grants are routing/authorization, not OS isolation.
