# Moonshine application-library comparison

> Classification scope: read this audit with the [ecosystem plan](../application-library-ecosystem.md) and [boundary review](boundary-review.md). A generic API or core gap below describes the inspected current interfaces/composition. It does not require product behavior in the shell or a mandatory dependency on bundled Catalog, Launch, NVHTTP or transport. Library, protocol, networking and packet delivery implementations are intended to remain independently replaceable.

Scope: Amaterasu checkout `f8aa56337288632df64db1cca807dd3b0cd6beaa` (working tree inspected; third-party submodule has preexisting state). Moonshine is a separate Rust, Linux-only Moonlight host acknowledging Sunshine's host-API groundwork, not established here as a Sunshine fork or as popular by a comparative metric. Inclusion is relevant host behavior, not a popularity ranking. [Moonshine README](https://github.com/hgaiser/moonshine/blob/main/README.md#faq). The upstream main README was inspected on 2026-10-31; GitHub's revision API was unavailable, so its current commit could not be independently pinned. Links to upstream main may drift. No runtime, installed-client, source build, or hardware verification was performed.

## Behavioral comparison

- **Existing coverage, with differences:** Moonshine documents manual title, argv, optional image, ordered synchronous pre/post commands and Steam integration, plus Steam and Lutris scanners. [Manual applications](https://github.com/hgaiser/moonshine/blob/main/README.md#adding-applications); [scanners](https://github.com/hgaiser/moonshine/blob/main/README.md#application-scanners). Amaterasu has catalog entries with name/description/tags, manual command and executable launch variants, preparation, per-app overrides and provider targets (`modules/catalog/src/model.rs:14`, `:64`, `:931`); Steam discovery supports all installed via an explicit option, bounded snapshot reconciliation and artwork (`modules/steam/README.md:76`, `:88`, `:127`, `:156`), and Lutris imports installed native/Flatpak games (`modules/lutris/README.md:1`). Exact command/hook failure ordering, Steam compositor integration and UI parity are not established by this comparison. Steam's discovery snapshot is not durable across module restarts (`modules/steam/README.md:243`).
- **Provider-implementable:** Moonshine also documents `.desktop` scanning (terminal and icon options), Heroic installed Epic/GOG/Amazon/sideload entries, and Bottles library/ready UMU entries, with local icons/cover art and launch-template details. Bottles excludes Steam shortcuts and warns external-prefix executables can end a session prematurely. [Scanner documentation](https://github.com/hgaiser/moonshine/blob/main/README.md#application-scanners). Implement these as independently built providers/importers with stable source IDs, source-specific filters, complete-scan criteria and launch handling; no need to bake store types into core. Catalog snapshot SDK supports batched entries and explicit finish/removal (`crates/module-sdk/src/application_library.rs:76`, `:128`); configured generic discovery routes (`modules/library/src/discovery.rs:9`) and opaque provider launch targets (`modules/catalog/src/model.rs:967`) exist. A route alone is not an importer or real provider (`docs/application-library-provider-configuration.md:22`). No built-in Heroic, Bottles or desktop scanner was identified in the inspected module inventory; a wider independent product inventory was not conducted.
- **Generic API gap:** Catalog `ArtworkReference` only accepts Steam, Lutris and Playnite (`modules/catalog/src/model.rs:94`), even though the SDK adapter defines generic discovery and artwork calls (`crates/module-sdk/src/application_library/provider_adapter.rs:18`, `:67`). The documented current library artwork path recognizes built-in types (`docs/application-library-provider-configuration.md:168`). An external scanner can publish entries without artwork, but cannot deliver its artwork through the normal catalog/library path merely by implementing that adapter. Catalog stores description/tags, but public SDK library rows and resolve project only ID and name (`crates/module-sdk/src/application_library.rs:32`, `:46`; `modules/library/src/lib.rs:112`). Rich client-visible metadata therefore needs an explicit supported projection, if desired; Moonshine's README only establishes title and image, not rich metadata parity.
- **Lifecycle coverage / provider obligation:** Launch supports provider incarnation, operation-based lookup/recover-stop/stop, fenced retirement assertions and fail-closed uncertainty (`crates/module-sdk/src/application_library/provider_lifecycle.rs:1`; `docs/application-library-provider-configuration.md:175`). An external provider must implement durable idempotency, reconciliation and fencing; SDK dispatch cannot prove actual effects (`crates/module-sdk/src/application_library/provider_adapter.rs:1`, `:60`). The synthetic example is not a real application importer or proof of restart cleanup (`docs/application-library-provider-configuration.md:3`). Moonshine's documented pre/post behavior does not establish equivalent crash recovery or retirement guarantees. The README identifies systemd as required to manage application processes; it does not establish equivalence to Amaterasu's proof contract.
- **Unknown / conditional core gap:** Moonshine's README does not establish per-client application selection, per-client capability policy, or simultaneous-client support (it says simultaneous clients are unsupported). Do not infer these features from pairing. [FAQ](https://github.com/hgaiser/moonshine/blob/main/README.md#faq). Amaterasu's library SDK list/resolve requests carry no client selector (`crates/module-sdk/src/application_library.rs:32`), and adapter identity is broker caller/initiator, not demonstrably a remote-client identity (`crates/module-sdk/src/application_library/provider_adapter.rs:53`). If product requirements demand per-client catalog filtering or launch authorization, trace authenticated client identity through list, artwork, resolve and launch before deciding whether a core identity/policy extension is necessary; this inspection does not prove every other Amaterasu layer lacks such policy. Provider adapter capability flags are service-call permissions, not per-client app entitlements.

## Minimal follow-up and acceptance

1. Add a versioned, bounded, opaque generic catalog artwork reference and startup-authorized route to the owning provider, preserving ownership, revision pinning, bounded transfer and release semantics; verify two independent providers, revision changes, stale/cross-provider references, denial, interrupted reads, and no path leakage. Do not claim generic artwork works before end-to-end qualification.
2. Build a separately reviewed scanner provider for each desired source. Test native/Flatpak locations and identities, stable IDs across updates/restarts, duplicates, partial/corrupt scans preserving existing rows, complete scans and removal, source-specific selection and launch arguments, icon fallback, and loss/restart/reconciliation of launch operations. Exercise actual installed launchers and real game lifetime separately from fixtures, particularly launcher exit and detached children.
3. Add client-aware policy only if requested: define broker-authenticated client binding, default policy and revocation; test identical list/resolve/artwork/launch enforcement, forged identifiers, reconnects, policy changes and stale IDs. No need to expose capture or encoder internals to implement library discovery.

Native components are trusted code; broker grants and provider assertions are routing/contract mechanisms, not a native-code sandbox. Existing source and documentation establish interfaces and intended behavior, not live game, graphical session, cleanup-after-crash, or third-party binary qualification.
