# Wolf / Games on Whales library audit

> Classification scope: read this audit with the [ecosystem plan](../application-library-ecosystem.md) and [boundary review](boundary-review.md). A generic API or core gap below describes the inspected current interfaces/composition. It does not require product behavior in the shell or a mandatory dependency on bundled Catalog, Launch, NVHTTP or transport. Library, protocol, networking and packet delivery implementations are intended to remain independently replaceable.

## Upstream behavior and relevance

* Wolf supports multiple concurrent sessions, with profile-specific application sets and persistent per-profile/app state; the special `moonlight-profile-id` supplies the Moonlight-visible catalog. Profiles have stable string IDs, display names and optional UI PINs. Apps describe process or Docker runners, optional compositor/audio/video setup, app state and icons. Icons may be local paths or URLs. [Wolf configuration](https://games-on-whales.github.io/wolf/stable/user/configuration.html#_profiles), [app definitions and icons](https://games-on-whales.github.io/wolf/stable/user/configuration.html#_defining_apps).
* Wolf UI browses profile apps, displays uninstalled items and downloads their Docker images, and organizes and updates apps. It creates cooperative lobbies for several users attached to one running instance. [Wolf UI](https://games-on-whales.github.io/wolf/stable/user/wolf-ui.html). Wolf documents disposable app containers with persistent mounted data. [Apps](https://games-on-whales.github.io/wolf/stable/apps/). The [API reference](https://games-on-whales.github.io/wolf/stable/dev/api.html) documents lobby IDs, initiator profile, optional PIN, connected sessions, runner, and stop-on-last-leave policy; the API uses a UNIX socket and can execute commands, so it is a privileged integration surface, not an ordinary public metadata endpoint.
* Dynamic application provisioning and runner implementation can live entirely in an independently trusted provider; parity does not demand that Amaterasu implement Docker, image fetching, mounts, registry discovery, or Wolf's API. Independent sessions and shared/co-op attachment require host/session capabilities if they are to be presented through Amaterasu itself. A provider-only UI such as Wolf UI may supply those experiences independently, subject to integration feasibility.

## Current boundary and gaps

1. **Existing:** catalog has durable importer/source-to-entry ownership markers, source generation and revision, staging and explicit removal state (`modules/catalog/src/product.rs:1-80`); SDK snapshot batches include stable `source_id` and distinct removals (`crates/module-sdk/src/application_library.rs:76-92,128-165`). Generic launch target is an opaque `(provider, application_id)` (`modules/catalog/src/model.rs:967-980`), bound to a configured importer and service (`modules/launch/README.md:171-179`). Provider-owned process, container, image and state-folder mechanics fit behind that target, given a provider that can meet the launch contract.
2. **Generic API gap—metadata/artwork:** provider discovery pages carry only ID, name and optional opaque artwork plus revision/cursor (`modules/library/src/discovery.rs:23-65`); the unified library projection only exposes ID/name (`crates/module-sdk/src/application_library.rs:17-51`). Catalog artwork is a closed Steam/Lutris/Playnite enum (`modules/catalog/src/model.rs:94-102`); generic discovery does not enable generic catalog artwork (`docs/application-library-provider-configuration.md:168-173`). No generic installed/available/provisioning/action metadata is exposed on this boundary. An implementation may independently retrieve remote data but cannot expose all of Wolf UI's library behavior through these current contracts.
3. **Generic API gap—identity and scoped catalogs:** discovery carries provider/cursor/limit, not a user/profile context (`modules/library/src/discovery.rs:23-29,104-125`); lifecycle carries operation/application/incarnation/ticket, not an authenticated profile or client (`crates/module-sdk/src/application_library/provider_lifecycle.rs:18-24`). Broker caller identity is component identity, not established end-user identity (`crates/module-sdk/src/application_library.rs:1-6,32-44`). Per-profile opaque IDs in a single global catalog are possible as provider-internal convention, but do not establish authorized per-user listing or launching. Preserve and validate identity across enumeration, artwork, launch, and operations; do not equate a Wolf UI PIN with a verified Amaterasu authorization primitive.
4. **Generic API gap—actions and events:** the public facade has list/resolve and launch is separate. SDK provider adapter offers discover/artwork and launch/lookup/recover-stop/stop (`crates/module-sdk/src/application_library/provider_adapter.rs:19-49`); no standardized negotiated install/update/uninstall, action status/progress/cancel, change event or subscription was found in these audited interfaces. Provider-owned polling and private UI are possible. Provisioning may outlast a launch request: expose capability-dependent durable operation IDs and reconciliation rather than pretending an accepted request finished installation. A revision-based rescan is a viable fallback if push events are unavailable.
5. **Core lifecycle gap:** launch pins incarnation and checks a trusted provider's matching fenced stop assertion, failing closed on ambiguity (`modules/launch/README.md:181-187`); it owns preparation and session leases. However launch state, operation idempotency and reconciliation are explicitly in memory and host crashes/provider reloads are unsupported (`modules/launch/README.md:379-384`). Durable catalog records therefore do not constitute durable launch/effect tracking. Provider's durable effect journal and recovery must be paired with host-side persisted ownership/session recovery; uncertainty must not be retired as success.
6. **Core capability gap—lobbies/multiple clients:** Wolf's lobby is a distinct shared instance with one or more connected sessions and last-leave policy. Current generic lifecycle requests represent one app operation and ticket; they do not express lobby creation, join/leave, participant authorization or shared-instance lifetime (`provider_lifecycle.rs:10-24`). The cited contract does not establish concurrent isolated capture/display/audio/input for different sessions or multiple clients attached to one instance. Inspect and qualify session/media/input capabilities separately before claiming co-op or multi-user parity. Neither a richer library row nor external container management alone creates those capabilities.
7. **Provider-dependent and unknown:** upstream profile/app identifiers and event delivery need verification against the actual target revision/API. Do not derive durable identity solely from mutable display title or URL; if source supplies no stable app identifier, the importer must persist a source-specific mapping and define rename/delete/recreate behavior. Whether a particular Wolf API deployment can safely reconcile a lost start, fence delayed requests, or prove all spawned effects stopped is not established by its docs; a conforming wrapper must implement and validate it rather than asserting proof merely from a missing process/container.

## Minimal extension and acceptance requirements

* Add versioned capability negotiation and bounded, revisioned provider metadata for availability/install state, supported actions, descriptive metadata and opaque artwork references. Route provider-owned artwork through authenticated fixed provider mapping and bounded byte/MIME/revision checks; never expose provider paths or make clients fetch arbitrary provider URLs. Verify remote artwork changes, missing image, disconnection, stale revision and cache invalidation.
* Use stable namespaced provider/source IDs and explicit deletion, complete snapshots and replay-safe generation/revision semantics. Test duplicate names, rename, reordering, incomplete or interrupted scans, uninstall versus temporary source outage, provider replacement/revocation and restart. Preserve catalog entry identity and user edits where intended.
* Add authenticated, authorized profile/user context to list, resolve, artwork, launch and actions, with consistent filtering at every route and cursor binding to scope/revision. Test two users with identical app names and private entries; deny guessing IDs, stale credentials and cross-profile operations. Provider policy remains responsible for its own external system credentials.
* Add optional asynchronous provider operations for install/update/remove, capability advertisement, progress, cancel and idempotent status/recovery; do not assume every provider implements every action. Test lost acknowledgments, retries, crash/restart, partial failure, external modification and cancellation races. Providers own the underlying provisioning and cleanup.
* Persist enough accepted launch and lease identity to reconstruct ownership across host/provider restart. Reconcile by exact provider incarnation, operation and effect identities; require a provider fencing/retirement assertion before releasing resources, retain unknown state for explicit retry, and never replay an ambiguous effectful start. Test crash at every admission/start/ack/stop boundary, including delayed starts and provider replacement. Provider assertions are trusted evidence, not OS-verified proof; native modules are trusted and API grants are routing/authorization controls, not a sandbox.
* For shared play as an explicit separate capability, model instance/lobby ID, owner/profile, join authorization, individual participant/session IDs, lifecycle events and configurable last-leave policy. Validate distinct join/leave, denial, disconnect/reconnect, stop while participants remain, concurrent independent instances and full media/input isolation on real clients. Support for only single-client launches should remain clearly reported as such.

These are source/doc-derived design requirements, not evidence of an installed provider, functional container launch, image download, full end-to-end streaming, hardware isolation or successful co-op gameplay. The included provider fixture is synthetic and explicitly does not establish real launch or cross-restart cleanup (`docs/application-library-provider-configuration.md:3-7,183-190`).
