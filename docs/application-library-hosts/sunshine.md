# Sunshine application-library audit

> Classification scope: read this audit with the [ecosystem plan](../application-library-ecosystem.md) and [boundary review](boundary-review.md). A generic API or core gap below describes the inspected current interfaces/composition. It does not require product behavior in the shell or a mandatory dependency on bundled Catalog, Launch, NVHTTP or transport. Library, protocol, networking and packet delivery implementations are intended to remain independently replaceable.

Scope: LizardByte/Sunshine upstream, not its forks. Amaterasu checkout main `f8aa56337288632df64db1cca807dd3b0cd6beaa`; source inspection only, no builds or live host tests. Upstream [master source](https://github.com/LizardByte/Sunshine/blob/master/src/process.cpp) and [API docs](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2api.html) were examined. ## Evidence and classification

- **CRUD and identity — partial support; provider management API gap.** Sunshine's [API](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2api.html) lists, saves and deletes apps by mutable array index, and closes the running app. Its [process parser](https://github.com/LizardByte/Sunshine/blob/master/src/process.cpp) computes IDs from content and has an index-based collision fallback; an import must not assume array indices or derived values remain stable across edits/reorders. Amaterasu has revision-checked owner CRUD (`modules/catalog/src/protocol.rs:5-53,215-303`), provider snapshots and source IDs (`crates/module-sdk/src/application_library.rs:76-92,128-165`), but library facade exposes only list/resolve (`crates/module-sdk/src/application_library.rs:17-50`), not generic provider configuration CRUD. A Sunshine importer can own persistent identity mapping and offer its own management service; editing the original source through a generic API is not currently provided. Match duplicates cautiously and flag ambiguous external edits instead of silently attaching one app's settings to another.
- **Launch/process — source-supported for core targets; provider implementable with qualification.** Sunshine's [application docs](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2getting__started.html) specify a single active app, termination on replacement, stream shutdown on app exit, process-less Desktop and detached behavior; its [context](https://docs.lizardbyte.dev/projects/sunshine/latest/structproc_1_1ctx__t.html) exposes working directory, wait-all, auto-detach and exit timeout. Amaterasu models executable, opaque provider and Desktop (`modules/catalog/src/model.rs:931-982,1015-1029`) and forwards executable lifecycle options (`modules/launch/src/workflow.rs:118-145`). A generic provider receives operation, app identity and incarnation, not a command (`modules/launch/src/workflow.rs:147-175`); it must implement process tracking itself and provide fenced terminal evidence (`crates/module-sdk/src/application_library/provider_lifecycle.rs:1-24,26-63`). Real process trees, launcher short-exit and platform-specific stop behavior remain unverified here.
- **Preparation, undo, environment, cwd, output/elevation — source support with parity limits requiring tests.** Sunshine supports global and app prep/undo, per-command elevation, exclusion, detached commands, working directory, output and environment substitutions ([parser](https://github.com/LizardByte/Sunshine/blob/master/src/process.cpp), [configuration](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2configuration.html), [getting started](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2getting__started.html)). Catalog represents these (`modules/catalog/src/model.rs:12-76,83-92,931-962`) and launch forwards environment and options (`modules/launch/src/workflow.rs:118-145,190-231`); cleanup is sequenced (`modules/launch/src/workflow.rs:329-400`). `Entry` is strict and prep steps bounded to eight (`modules/catalog/src/model.rs:5-9,12-14`): imports exceeding bounds need explicit diagnostics, not truncation. Sunshine shell-string conversion, `$(VAR)`/`$$` expansion, default cwd, global env precedence, elevation, do-failure and reverse undo require end-to-end comparison on each platform; representation alone is not parity. Generic lifecycle requests carry no stream/client context or launch environment, so dynamic provider-owned process configuration needs a deliberate versioned contract or host-owned preparation; avoid double execution.
- **Artwork — generic API/core integration gap.** Sunshine supports PNG paths and cover upload ([API](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2api.html)). SDK declares generic reference and bounded revision-pinned artwork chunks (`crates/module-sdk/src/application_library.rs:267-281,321-371`), yet catalog and library artwork route only Steam, Lutris and Playnite (`modules/catalog/src/model.rs:94-102`; `modules/library/src/artwork.rs:10-16`; `docs/application-library-provider-configuration.md:168-173`). Therefore a Sunshine provider cannot publish generic catalog artwork through the existing normal export path merely by implementing the SDK; this is a concrete host integration gap. Upload, persistence, revisions and authorization also need an actual management path.
- **Discovery/import/sync/filtering — provider implementable, not shipped Sunshine import.** Sunshine documents manual UI/apps.json configuration ([getting started](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2getting__started.html), [configuration](https://github.com/LizardByte/Sunshine/blob/master/docs/configuration.md)); no automatic store discovery or install workflow is established by the reviewed sources. Generic discovery has provider, cursor and limit only (`modules/library/src/discovery.rs:23-29,104-125`), and page projections have ID/name/art (`crates/module-sdk/src/application_library.rs:267-291`). Snapshots support staged or incremental publication with explicit stale cleanup (`crates/module-sdk/src/application_library.rs:8-11,128-165`). A provider can parse apps.json and filter locally, but no standardized import configuration, query/filter expression, change subscription or source-edit sync API exists in this boundary. Ensure a failed or incomplete scan cannot delete prior entries.
- **Ordering, visibility, access, metadata — generic API gaps; upstream extent unknown.** Sunshine's documented UI operates on its apps array via indexed edits; its [parser](https://github.com/LizardByte/Sunshine/blob/master/src/process.cpp) iterates that array. Do not infer a per-client hide/access feature or guaranteed client display order from that alone. Amaterasu's generic row is ID/name only (`crates/module-sdk/src/application_library.rs:32-50`); catalog stores description/tags and overrides (`modules/catalog/src/model.rs:12-27,64-75`) but generic discovery cannot transmit rich metadata, source order, visibility, or client-scoped rules (`modules/library/src/discovery.rs:23-29,51-65`). Need explicit semantics before claiming those cross-provider features, and separate admin metadata from safe client projection.
- **Profiles and events/install — unknown upstream; no invented requirement.** Sunshine's documented app schema includes execution configuration, not evidence in the reviewed sources of per-client app profiles, app installation actions, or a library event stream ([API](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2api.html)). Amaterasu stores app-specific configuration overrides (`modules/catalog/src/model.rs:28-75,144-166`), while generic lifecycle has no client/profile context (`crates/module-sdk/src/application_library/provider_lifecycle.rs:17-24`). Additional per-client selection, install/action and notification APIs should be driven by independently verified host needs, with authorization and completion semantics; do not label Sunshine as supporting them on this evidence.
- **Replacement boundary — development facility, not production proof.** The bundled example is synthetic and cannot prove real app launch or restart cleanup (`docs/application-library-provider-configuration.md:3-9,49-55`). Explicit Linux development-set replacement exists (`docs/application-library-provider-configuration.md:193-210,237-250`); production trust management and independent publisher mixing are outside that path (`docs/application-library-provider-configuration.md:110-120`). Generic import and provider launch need startup mappings and broker checks (`docs/application-library-provider-configuration.md:122-163,175-189`); native modules are trusted, and a retirement assertion is provider evidence, not OS verification.

## Concrete acceptance requirements

1. Import an apps.json fixture with duplicate names, reordered entries, edit/delete/re-add and collision ambiguity. Persist stable provider source IDs and revisions; report conflicts and preserve existing associations when identity cannot be established. Exercise stale/partial snapshot, retries, and concurrent admin edits.
2. Round-trip and run executable, process-less desktop, short-lived launcher with auto-detach, wait-all child tree, detached commands, global plus per-app prep/undo and exclusion, app output, cwd, environment interpolation/escaping and elevation on supported platforms. Verify abort and rollback after each failing prep step, stop timeout, disconnect and restart/unknown start; record unsupported values rather than silently losing them.
3. Add a provider-neutral catalog artwork identity and authorized route keyed by selected provider plus opaque ID/revision. Test complete bounded PNG transfer, stale revision, changed content, invalid chunks, denied callers and removal, including an actual client artwork read; the SDK type alone is insufficient.
4. Define a versioned provider management/read/write contract only if host UI must edit provider-owned apps: capability negotiation, source identity and revision, optimistic concurrency, lossless unsupported fields, validation/errors, and explicit delete versus local hide. Alternatively ship a provider-specific management surface and document that boundary.
5. If supporting ordered lists, filtering, visibility, richer metadata or client policies, define stable pagination and consistent list/resolve/launch authorization first; preserve source order and never expose private launch commands. Client identity/context must be broker-attested. Add explicit lifecycle context only with ownership and recovery semantics.
6. Qualify a separately built real provider: import, launch, monitor, stop and reconcile across provider/host restart and lost response with durable fencing; prove route/initiator checks, cleanup uncertainty retention and replacement packaging. Existing synthetic example and source models are not runtime or hardware verification.
