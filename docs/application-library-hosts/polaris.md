## Reference behavior

- Polaris imports installed Steam, Lutris, Heroic and registered ROM folders, stages candidates, retains identities and launch context, and offers rescan; a launcher or emulator is also published so users can manage installation or sign-in. ROM import deduplicates and reports missing emulator requirements; Heroic preserves native/Flatpak runner and installation identity. https://papi-ux.com/docs/apps/ ; https://papi-ux.com/docs/emulators/ ; https://github.com/papi-ux/polaris/blob/master/README.md
- The host library presents source and launch health, favorite/recent/readiness ranking, explicit published ordering and per-game configuration. Nova offers enhanced host-backed presentation and launch choices; ordinary Moonlight has the compatible browse/launch subset. Per-app options include gamepad overrides, commands and reversible preparation, runtime exit behavior and display policy. Device permissions and experimental per-player Spaces are separate host/session features. https://papi-ux.com/docs/apps/ ; https://github.com/papi-ux/polaris ; https://papi-ux.com/docs/spaces/ (preview availability depends on host/runtime).
- Artwork includes poster, background, logo and icon, with source precedence, manual choices, opt-out and review of proposed matches; cover-only updates do not stop a running game. ROM sidecars and other local front-end caches can supply covers. https://papi-ux.com/docs/apps/ ; https://papi-ux.com/docs/library-and-artwork/
- A disconnected stream can retain its game for resume; ending a session targets the game owned by that session. Install is documented here through publishing the launcher, not a verified Polaris generic install API or progress event contract. No assertion is made that Polaris exposes install actions, ordered change events, or quantitative progress through a generic protocol. https://github.com/papi-ux/polaris ; https://papi-ux.com/docs/apps/

## Amaterasu evidence and classification

- **Existing foundation, not complete parity.** Catalog entries already support name/description/tags, selected overrides, launch forms, prep commands and provider targets (`modules/catalog/src/model.rs:14`, `:65`, `:933`, `:967`). Catalog supports create/update/delete, search and revision-checked, staged provider snapshots (`modules/catalog/src/protocol.rs:7`, `:59`, `:64`). Public catalog export projects only ID and name (`modules/catalog/src/protocol.rs:500`); SDK library list/resolve likewise exposes only those fields (`crates/module-sdk/src/application_library.rs:16`, `:36`, `:47`). Do not infer rich client support from stored administrative metadata.
- **Provider-implementable with present building blocks.** A separately built provider can discover local stores or ROMs, assign stable opaque identities, perform selection and import into catalog, and implement launcher-specific launch/stop. SDK discovery pages contain ID/name and one optional artwork reference and are revision-pinned (`crates/module-sdk/src/application_library.rs:249`, `:261`, `:270`, `:287`); discovery routing is configured explicitly (`modules/library/src/discovery.rs:84`, `:124`). A discovery route alone does not import: `docs/application-library-provider-configuration.md:22`. The example is synthetic and does not qualify real launch or restart recovery (`docs/application-library-provider-configuration.md:3`). Existing individual Steam/Lutris integrations should not be assumed to cover Heroic/ROMs without separate verification.
- **Generic API gap: artwork.** SDK chunks are bounded and revision-pinned (`crates/module-sdk/src/application_library.rs:326`), but catalog artwork is an exhaustive Steam/Lutris/Playnite enum with one reference (`modules/catalog/src/model.rs:94`), and library routing uses that catalog reference (`modules/library/src/lib.rs:537`; `modules/library/src/artwork.rs:43`). A generic provider's discovered reference therefore does not by itself establish published generic artwork support, multiple roles, custom override or match-review workflows.
- **Generic API gap: catalog semantics.** The SDK projection lacks source identity/provenance, installation and readiness state, capabilities/blocked reasons, rich metadata, per-player visibility, ranking/order, change events, and generalized provider actions/progress. The catalog entry schema denies unknown fields (`modules/catalog/src/model.rs:12`); a provider cannot assume arbitrary metadata survives snapshots. Verify other interfaces separately before claiming these are absent everywhere.
- **Lifecycle foundation and core integration work.** Provider launch/lookup/stop/recover-stop is operation- and incarnation-bound; retirement is a trusted provider assertion and delayed launches must be fenced (`crates/module-sdk/src/application_library/provider_lifecycle.rs:1`). Catalog provider target carries provider and opaque application ID (`modules/catalog/src/model.rs:967`). Session-level pause/resume and resource cleanup are separate from provider process ownership: qualify actual disconnect/resume, stop-only-owned-process, crash/restart recovery and composed host resources end to end before claiming Polaris parity. A provider cannot by itself deliver Nova-compatible UI, device authorization, multi-user Space isolation, compositor or transport behavior.
- **Authorization is not sandboxing.** Native modules are trusted; service grants route calls, and providers must validate broker-attested caller, initiator and action (`docs/application-library-provider-configuration.md:75`). Player/device permissions and profile isolation need host-enforced checks in their own subsystems.

## Durable needs and acceptance targets

1. Version a generic, optional capability-negotiated provider contract for stable provider/source IDs, source/runner/install identity, install/readiness and actionable blocked reasons. Pages must remain bounded, revision-consistent and distinguish failed/partial scans from complete ones. Acceptance: two independent fixture providers, including ROM and launcher, retain distinct IDs across rescans; incomplete scans never delete unseen entries; user edits survive provider updates.
2. Add a safe rich client projection with explicit visibility and permissions scoped to requesting user/device, ordered/paginated results and revision or resumable change notifications. Define whether order is provider or user owned and reconcile concurrent edits; never expose commands, credentials or paths by default. Acceptance: clients see only authorized entries, reconnect after missed updates converges to a snapshot, reordering and artwork refresh do not terminate an active stream.
3. Generalize catalog artwork references to provider-scoped opaque ID/revision and role (poster/background/logo/icon), with bounded validated streaming and explicit custom/automatic precedence, removal opt-out and conflict-safe choice. Acceptance: a third-party provider serves artwork without host hardcoding its name, stale chunks are rejected, manual selections survive rescans and concurrent edits, failed match proposals make no changes.
4. Add optional typed action discovery only where product requires install/update/uninstall and progress: authorization, idempotency, job IDs, terminal/unknown/cancel states, recovery and bounded progress. The default is unsupported, not simulated success; do not imply Polaris documents this capability. Acceptance: retry after timeout cannot duplicate effects; denied users cannot start or observe jobs; disconnect/restart yields truthful state.
5. Preserve per-app settings and distinguish stored intent from verified runtime launch readiness. Bind any preflight choice to app and catalog revision, revalidate at launch, report actionable refusal. Test provider launch ownership, disconnect/resume and explicit stop, failed cleanup, restart and stale incarnation against a real provider and actual host before reporting runtime parity.
6. Treat Spaces as a separate optional host capability with explicit user/launcher identity, isolation and session capacity, not a provider metadata flag. Record client protocol and runtime compatibility separately; no Nova interoperability established by this audit.
