## Reference behavior and limits

* Foundation describes itself as a Sunshine-based host optimized for Windows, with a standalone desktop GUI consolidating game library management ([README](https://github.com/AlkaidLab/foundation-sunshine/blob/204a96826606b3a34cf2cd813aed0f0a9bba7db0/README.md)). Its guide says the desktop Applications page scans Steam, Epic and GOG and local folders, lets users inspect and select or add all results, and refreshes the client list; browser management cannot invoke that local desktop scan. It also documents manual named app/program creation and built-in app restoration. These are documented behaviors, not tested here.
* The Foundation [usage guide](https://github.com/AlkaidLab/foundation-sunshine/blob/204a96826606b3a34cf2cd813aed0f0a9bba7db0/docs/getting_started.md) describes command/cwd/env, preparation failure abort, tracked process termination ending the stream, detached commands, and a commandless Desktop. Distinguish its stated behavior from any provider-specific runtime observed on a real system.
* Foundation merged [AI-assisted game metadata scraping](https://github.com/AlkaidLab/foundation-sunshine/pull/747) and release notes include [remote cover localization](https://github.com/AlkaidLab/foundation-sunshine/releases/tag/v2026.911.85650.%E6%9D%82%E9%B1%BC); they establish feature work, not complete current cover search/upload semantics. Current GUI details, per-client categories/order/filter/events, exact AI sources, and process lifecycle edge cases require pinned source and runtime qualification. Do not claim these are all Foundation features merely because they are useful extension requirements.

## Amaterasu evidence and classification

* **Supported building blocks:** Catalog has revision-checked create/get/update/delete, search, export, and provider snapshot operations (`modules/catalog/src/protocol.rs:7-63`); entry model includes description, tags, per-app configuration/display overrides, prep/do/undo/elevation and launch target (`modules/catalog/src/model.rs:14-76`). Launch orchestrates bounded global/app preparation, reverse undo and process/session ownership (`modules/launch/README.md:50-76`, `:119-140`). This is not by itself proof of Foundation behavior or real installed-game operation.
* **Provider-implementable:** Independent trusted provider can scan Windows Steam/Epic/GOG or selected folders, present selection in its own UI, then submit authenticated mapped snapshot imports and lifecycle target. SDK snapshots include source IDs, generations/revisions, sequence and stale/removal decisions (`crates/module-sdk/src/application_library.rs:76-92,128-165`); discovery is opt-in and initiator-routed (`modules/library/src/discovery.rs:1-29,82-110`). A scanner failure must not masquerade as complete and prune entries; partial incremental snapshots are not automatically rolled back (`crates/module-sdk/src/application_library.rs:1-11,283-290`).
* **Generic API gaps:** The public facade exposes list/resolve, discovery and artwork transfer (`modules/library/src/lib.rs:23-48`); exported list/resolve projects only ID/name (`crates/module-sdk/src/application_library.rs:17-51`), and discovery only ID/name/opaque artwork (`:257-290`). Catalog search and management CRUD are separate privileged operations, not unified facade functions. Neither discovery contract nor list rows provide installed status, source labels, categories, filters, metadata provenance, import previews or selection commits. Do not infer that lower-level catalog search is absent.
* **Core interoperability gaps:** Catalog artwork references are a closed Steam/Lutris/Playnite enum (`modules/catalog/src/model.rs:94-102`); generic discovery does not enable generic artwork routing (`docs/application-library-provider-configuration.md:168-173`). A provider cannot currently make arbitrary source artwork appear via that standard catalog path without extending/replacing relevant consumers. The snapshot entry schema is closed; arbitrary metadata cannot simply be appended. Explicit shared contracts are needed for portable persistent user metadata, ownership/merge and per-client library views/events. Per-client launch/display override logic exists (`modules/launch/src/pipeline.rs:41-54`) but does not establish per-client catalog categories or ordering.
* **Lifecycle trust and qualification:** Catalog binds provider identity to authenticated import provenance; launch rechecks route and owns preparation/session. Lost starts lead to fenced stop; uncertain cleanup retains lease (`docs/application-library-provider-configuration.md:175-189`). Native modules are trusted code; grants route authority, not a native-code sandbox (`crates/module-sdk/src/application_library.rs:1-6`). Fixture qualification explicitly excludes real artwork, game effects, playback, installation and end-to-end gameplay (`docs/application-library-provider-configuration.md:294-309`).

## Extension requirements and acceptance

1. Version capabilities and paginated, revision-pinned provider discovery with stable provider/source identity, installation state, source labels, typed optional metadata and source-specific errors. Provide explicit preview/select/add-all, deduplication and per-source outcomes; preserve user edits and other providers across rescans. Test duplicate names across sources, empty pages, changed revisions, interrupted/unavailable scans, disconnected disks, partial success and stale cleanup only after a complete authoritative scan.
2. Define authorized management create/read/update/delete and search projections separately from client-safe list/resolve; expose provenance, display fields and writable override masks without exposing commands or local paths to untrusted clients. Revision conflicts must not overwrite concurrent edits; test pagination while updating, permissions, import/restore and source ownership.
3. Extend artwork to provider-keyed opaque ID/revision references and routed bounded chunk read/release; add explicitly authorized search, choose, upload and local-cover persistence, MIME/content/size validation, controlled remote fetch and cache lifecycle. Preserve user-selected artwork during rescans. Test chunk continuity and revision changes, malicious/oversize files and URLs, interrupted uploads, provider replacement and missing assets. Search/upload are proposed requirements, not asserted Foundation parity.
4. Specify process target/start/status/stop and cancellation reconciliation through the existing launch coordinator, with stable operation IDs, incarnation fencing, retained leases on ambiguous cleanup, ordered preparation and reverse undo. Exercise tracked/detached children, app exit, prep failure, provider crash/restart, lost acknowledgement, duplicate retries and multi-client disconnect/resume on real hosts; verify user-visible launch and cleanup, not merely provider assertions.
5. Define typed per-app and per-client profile/visibility, categories/tags, ordering, query and notifications only where supported by explicit policy; specify precedence, identity, persistence, revision/cursor invalidation and reconnect/resync. Test two paired clients with independent view preferences, authorization, reorder conflicts, event gaps/replay and backward-compatible clients. No claim Foundation implements these semantics without further evidence.
