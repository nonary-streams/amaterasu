# Cross-host boundary review

Source review at Amaterasu main `f8aa56337288632df64db1cca807dd3b0cd6beaa`. No implementation or tests. The key correction is to separate **replaceable library behavior**, **existing consumer contract**, and **shared host services**. A replacement can own a database, imports, merging/overlays, sync, ordering, provider routing, metadata, artwork storage and optional actions internally without changing Catalog's schema. It can expose richer operations on a separately versioned service to suitably approved new consumers. That is an architectural possibility, not something the read-only fixture proves, and those features cannot automatically reach existing consumers.

## What selection actually replaces

- The Linux development packer selects a separately built provider of `amaterasu.library/1`, rewrites dependencies in a signed complete set, and requires explicit caller/provider grants and `library_principal` bindings; selection activates at a worker boundary, not a live swap (`docs/application-library-provider-configuration.md:193-215,246-272`). The fixture supports list/resolve only and has not proved artwork, launch or discovery (`docs/application-library-provider-configuration.md:274-281,294-309`). Native code is trusted.
- NVHTTP calls the replaceable library facade for list and artwork. Replacements implement `artwork_open` with the [shared binary artwork contract](../artwork-transfer.md); Catalog-specific references remain a constraint only of the bundled facade. Revisions are opaque bounded strings, and binary record size/MIME/framing are validated by the common SDK.
- A replacement serving the current NVHTTP consumer must honor its list validators: strict ID/name-only response and cursor shapes, fixed numeric `app-` IDs, ascending IDs, matching cursor and revision, no empty intermediate page (`modules/nvhttp/src/wire/applications.rs:19-41,66-124,176-210`). Adding rich fields to `/1` fails due to `deny_unknown_fields`. A replacement may maintain private order, but cannot expose arbitrary source order through this legacy list without changing NVHTTP. The SDK comment says follow even empty pages (`crates/module-sdk/src/application_library.rs:21-23`), whereas NVHTTP rejects an empty page with a continuation; reconcile this documented/consumer mismatch as part of qualification.
- Crucially, replacing the library does **not** replace launch or Catalog: NVHTTP's launch path passes a numeric catalog ID to launch, which resolves the trusted Catalog owner (`modules/nvhttp/README.md:615-620`). Provider targets additionally require current launch route plus matching importer/source provenance (`modules/launch/src/pipeline.rs:1537-1559`; `docs/application-library-provider-configuration.md:175-181`). For the current bundled NVHTTP/Catalog/Launch composition, a replacement with its own IDs/data must publish matching authorized catalog launch entries or supply separately integrated launch architecture; list/resolve success alone cannot prove launch. The fixture's static `example-game` ID (`crates/module-sdk/examples/application-library-replacement/src/lib.rs:49-65`) is not a valid NVHTTP canonical numeric catalog ID; catalog-backed mode validates canonical IDs (`:74-120`).
- Management's existing fixed routes read/write Catalog, not an arbitrary library replacement (`modules/management/src/server.rs:1290-1305`; `modules/catalog/src/protocol.rs:5-53`). Signed UI extensions can dispatch an approved method to an approved service, with manifest, exact policy and authenticated scope/role checks (`modules/management/src/extensions.rs:96-135,149-153`; `modules/management/src/server.rs:840-893`). Thus replacement-specific management UI/actions can exist without broad core schema growth **if configured, granted and implemented**; existing catalog UI does not gain them automatically.

## Priority critique

1. **P0 artwork:** preserve `/1` artwork transfer compatibility when supporting the existing NVHTTP consumer. Prioritize provider-neutral Catalog attachment/routing if multiple independent providers must work through the bundled Catalog-backed library, rather than declaring it indispensable for replacement-owned artwork. Validate identity, route, revision and chunk stream, revoke/transfer cleanup and client read.
2. **P0 rich metadata, provenance and user overlays:** keep source-specific richness, merge policies and overlays behind the selected implementation initially. Promote only common data consumers actually need into a versioned read/edit contract. Catalog already has authenticated provider snapshot ownership and a restricted provider override operation (`modules/catalog/src/pipeline.rs:292-314`); its current fixed schema is not a general metadata store. A shared authoritative provenance contract is needed only when cross-component launch/authorization relies on it, and cannot be trusted merely because an untrusted payload names a provider.
3. **P0 rich query:** a new versioned consumer service can support metadata, filters, ordering and pagination owned by the replacement; no Catalog schema change is inherently needed. The current NVHTTP GameStream implementation requires its `/1` compatibility projection and stable numeric mapping; another protocol adapter can define its own negotiated mapping. Describe snapshot revision, cursor query binding, deterministic order, change/conflict behavior and access rules. Consumer access and approved calls must be explicitly configured. Avoid changing legacy row fields in place.
4. **P0 authenticated device/user/session context:** shared change is necessary only when host-controlled consumers must convey these identities across their component boundaries or enforce consistent per-device list/launch access. Broker attests component caller/initiator, not automatically the external human/device (`crates/module-sdk/src/application_library/provider_adapter.rs:141-146,170-201`); generic lifecycle carries app, operation, incarnation and ticket but no client (`crates/module-sdk/src/application_library/provider_lifecycle.rs:17-24`). NVHTTP currently keeps exact certificate ownership itself (`modules/nvhttp/README.md:615-625`), and artwork calls contain no device identity (`modules/nvhttp/src/wire/artwork.rs:144-151`). Design a host-issued scoped context/capability, validate issuer, audience, binding, lifetime, revocation and replay, and use consistent authorization at list, artwork, resolve and launch. Do not accept payload-asserted identity as broker proof. Avoid forcing provider access to device details when host policy suffices.
5. **P1 actions/source management/change cursor:** replacement-private services plus approved management extensions can implement these now; a generic interoperable contract is needed when common consumers must control arbitrary providers. Add optional capabilities only for demonstrated needs: explicit permission, idempotent operation identity, bounded status/progress, cancellation and recovery with unknown outcome, and cursor retention/expiry plus full rescan on gaps. Do not assume a provider can safely roll back installation or that an event stream is durable.
6. **Concurrent sessions/multiseat/lobbies:** correctly separate from library semantics. Implement only with independent session/resource isolation, authorization, process/effect ownership and cleanup proof; a richer library or replacing the facade does not supply host concurrency.

## Minimum stable boundary and migration

- Keep `/1` list, resolve and artwork wire behavior and canonical ID mapping stable for existing consumers; validate full multipage list and end-to-end artwork and launch with a real replacement. IDs must remain bound to the same authorized launch target across restarts, changes and replacement; define migration and conflict handling rather than silently recycling IDs.
- Introduce a separately named/versioned rich read service with explicit capability/version discovery and safe client projection. At minimum define stable application identity, source namespace, revision-consistent bounded list/resolve, an opaque query-bound cursor, and structured errors. Add artwork or management only as separately negotiated capabilities; keep provider-specific fields opaque and avoid exposing paths, commands or private credentials.
- Define capability negotiation as advertised support plus explicit startup authorization and successful operation; absence or unknown versions mean unsupported, never infer grants. Preserve old consumers during rollout; consumers select supported versions explicitly and fail closed for authorization, identity or incomplete scans. Do not overload broker principal identity with end-user identity.
- Acceptance: exercise a replacement-owned metadata/overlay database and custom action via approved extension without Catalog schema changes; simultaneously serve `/1` list/artwork and, when using the current bundled launch route, map the same canonical ID to an authorized Catalog launch; and test revocation, pagination mutation, forged identity, mismatched provenance, provider restart and unconfirmed cleanup. Establish behavior on unavailable capabilities rather than relying on the synthetic example.

## Architectural correction: independently replaceable components

The long-term target is independent, separately selected library, management, launch/execution, client-protocol, and network/packet-delivery components. The shell supplies generic loading, routing, capability/version negotiation and lifecycle facilities; it must not require built-in Catalog, NVHTTP, Steam or any particular wire protocol. This is intended architecture, not a claim that the current release tooling already packages, selects or safely swaps every one of these components. The development library replacement documented above is the verified scope of that specific selection facility.

- **Library:** independently owns its identities, records, metadata, artwork and policy, subject to the chosen common semantic contracts. It exposes bounded versioned application/read/management capabilities, not packet APIs. Internal storage and provider composition remain its choice.
- **Management:** consumes negotiated library/admin capabilities through approved authorization, and may itself be independently replaced. The current fixed Catalog editor and signed extension mechanism are examples of today's composition, not requirements on all implementations.
- **Launch/execution:** independently consumes an authorized, versioned launch intent/target and owns execution, stop, recovery and effects. The chosen library and launcher need a validated identity-to-target handoff with clear authority, stable operation identity, lifecycle evidence and revocation. Neither a Catalog record nor the current provenance wire shape should be mandated for every composition; adapters may translate where the selected endpoints differ. A matching Catalog record is required for the specific current bundled route, as described above.
- **Protocol and network/delivery:** a protocol adapter translates its client's authentication, app-list, artwork and launch requests to negotiated semantic services; a separately owned networking/delivery component handles transport and packet delivery. The library does not call packet APIs and need not know GameStream, numeric app IDs, sockets, Steam, or an NVHTTP service name. A GameStream adapter may own persistent numeric aliases and the exact legacy projection, keeping protocol-specific ordering/constraints out of the general library contract. Protocol and transport may be separate selections where their negotiated contracts support it; this review has not established current replaceability or integration tooling for either.
- **Compatibility and composition:** keep existing `/1` and current validators for installations choosing current NVHTTP, while an adapter bridges a richer selected library to that consumer. Independently negotiate required service versions and optional capabilities with explicit policy/authorization. Fail composition clearly when no compatible adapter exists; do not silently require a bundled component, infer capabilities from component names, or treat advertised capabilities as grants. Externally authenticated scope must cross relevant boundaries as a host-verifiable scoped context when required, without exposing credentials or forcing identity disclosure to unrelated components.

## Integration disposition

The integrator incorporated the architectural corrections into the final
[ecosystem plan](../application-library-ecosystem.md). The earlier draft's line
references are intentionally omitted because they no longer identify that plan.

- Current NVHTTP validators, numeric aliases and Catalog launch records are scoped
  to that optional composition; alternate protocol/launch plugins may negotiate
  another authorized semantic handoff.
- Provider-neutral Catalog artwork is an interoperability improvement for the
  bundled path, not a prerequisite for replacement-owned artwork.
- Library, management, launch, protocol, networking and packet delivery retain
  independent ownership. The library has no packet API dependency or mandatory
  Catalog, NVHTTP or Steam dependency.
- Versioned interoperability profiles and independently swappable contract
  fixtures should qualify composition. The intended architecture is distinct
  from the development library replacement already demonstrated by tooling.

This report and plan are research artifacts, not implementation or runtime proof.
