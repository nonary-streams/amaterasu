## Requirements and disposition

* **Source sync — implemented in parts; provider-implementable policy.** Vibepollo Playnite has installed/recent count and age, include/exclude categories, plugin IDs and game IDs, uninstall removal, TTL and replacement policy ([config_playnite.h:18](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/config_playnite.h#L18)); Steam and Lutris reconcile only managed rows with exclusions, preserving manual/other-provider rows ([steam_sync_policy.h:12](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/steam_sync_policy.h#L12), [lutris_sync_policy.h:11](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/lutris_sync_policy.h#L11)). Amaterasu has authenticated importer/source markers and staged per-source upsert/removal/expiration intents ([product.rs](../../modules/catalog/src/product.rs#L175), [application_library.rs](../../crates/module-sdk/src/application_library.rs#L76), [pipeline.rs](../../modules/catalog/src/pipeline.rs#L824)). These support independent provider selection/reconciliation, but the generic discovery `Application` exposes only ID/name/artwork, not categories, last-played/install status or source-specific metadata ([application_library.rs](../../crates/module-sdk/src/application_library.rs#L267)). A provider can retain/filter metadata internally; a generic UI for source metadata and policies needs a versioned extension schema and discovery/configuration capability, rather than inventing fixed fields for every source. Existing bundled Steam/Lutris/Playnite policy parity is not established by this inspection.

* **Artwork and editor — generic API gap.** Vibepollo exposes manual library management and artwork, while UUID is stable across artwork changes and ArtVersion or numeric alias invalidates cache ([migration doc](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/docs/gamestream_migration.md#L21), [nvhttp.cpp:4667](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/nvhttp.cpp#L4667)). Amaterasu's SDK has bounded revision-pinned artwork chunks ([application_library.rs:249](../../crates/module-sdk/src/application_library.rs#L249)), yet catalog artwork is an enum restricted to Steam/Lutris/Playnite ([model.rs:94](../../modules/catalog/src/model.rs#L94)); catalog rejects unauthorized writes and checks importer/source identity ([protocol.rs:328](../../modules/catalog/src/protocol.rs#L328), [pipeline.rs:3375](../../modules/catalog/src/pipeline.rs#L3375)). Its own provider guide explicitly says generic discovery does not enable generic catalog artwork routing ([guide:168](../application-library-provider-configuration.md#L168)). Add an opaque provider-key/source-bound reference and route plus explicit user-owned cover override with safe bounded ingestion and revisions; keep provenance and untrusted bytes checked. Confirm existing editor behavior before defining exact UI scope.

* **Stable UUID, ordering, cache identity — core/protocol gap.** Vibepollo app projection sends UUID, IDX, ID and ArtVersion, including optional legacy ordering and role-sensitive projection ([nvhttp.cpp:4616](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/nvhttp.cpp#L4616)); its editor persists reordered UUIDs ([apps.html:776](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src_assets/common/assets/web/apps.html#L776)). Amaterasu library public projection only supplies `id` and `name` ([application_library.rs:46](../../crates/module-sdk/src/application_library.rs#L46)); NVHTTP insists on ascending numeric IDs and emits only title, ID and HDR ([applications.rs:108](../../modules/nvhttp/src/wire/applications.rs#L108)). Introduce a stable persistent app UUID distinct from source IDs and numeric transport aliases, durable artwork version and ordered export; evolve pagination without exposing command metadata. Verify actual legacy client ID/cache behavior before committing alias strategy.

* **Per-client visibility, permissions, profiles — core authorization/projection gap; current extent unknown.** Vibepollo's catalog filters on active state then projects based on verified client, view/launch permissions and current app owner ([nvhttp.cpp:4572](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/nvhttp.cpp#L4572), [nvhttp.cpp:4616](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/nvhttp.cpp#L4616)); its editor offers per-client app identity ([apps.html:495](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src_assets/common/assets/web/apps.html#L495)). Do not infer from this that Vibepollo already implements arbitrary app-by-client ACLs: that remains unverified. Amaterasu already performs certificate and launch permission checks ([wire.rs:363](../../modules/nvhttp/src/wire.rs#L363)) and supports app/client configuration precedence ([pipeline.rs:41](../../modules/launch/src/pipeline.rs#L41)); its public library request/entry lacks client identity and ACL data. If per-app grants are desired, trusted host mediation must consistently apply certificate-bound policy to list, resolve, artwork, launch, resume and terminate; hiding a tile alone must never authorize a launch. Define identity scoping and ownership independently from provider data. Retained owner reconnect and safe replacement remain explicit qualification cases.

* **Custom launch, prep, undo and lifecycle — substantial infrastructure exists; provider and runtime qualification required.** The catalog includes app configuration and bounded raw preparation/undo ([model.rs:12](../../modules/catalog/src/model.rs#L12), [model.rs:83](../../modules/catalog/src/model.rs#L83)); workflow schedules provider stop and reverse undo ([workflow.rs:329](../../modules/launch/src/workflow.rs#L329)). Vibepollo includes global/app and client prep/undo, client identity environment and managed app focus ([apps.html:350](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src_assets/common/assets/web/apps.html#L350), [apps.html:541](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src_assets/common/assets/web/apps.html#L541), [managed_app_focus.cpp](https://github.com/Nonary/Vibepollo/blob/c5e4f21632f0d22a8e91bb89b7df357a0bd677d7/src/managed_app_focus.cpp)). The provider lifecycle requires stable incarnation, operation deduplication, matching ticket and fenced retirement ([provider_lifecycle.rs:1](../../crates/module-sdk/src/application_library/provider_lifecycle.rs#L1)); it is a trusted provider assertion, not OS proof or a native-code sandbox. The included generic example is synthetic and cannot prove real launch or restart cleanup ([guide:4](../application-library-provider-configuration.md#L4)). Provider-specific focus, emulator ownership, child/process tree termination and restart recovery require independently implemented providers and real platform qualification; no equivalence is claimed.

* **Restore/deletion — unknown parity.** Determine whether Vibepollo's system-app restore or any app/client profile backup applies to this branch and compare Amaterasu persisted catalog deletion/reimport semantics. Do not equate lifecycle undo with restoring deleted application profiles. Preserve user edits, stable identity and covers across deletion/reimport and provider outages where the chosen policy requires restoration; test explicitly.

## Bounded implementation and acceptance plan

1. Inventory current built-in Steam/Lutris/Playnite and management/editor behavior, stable ID persistence and permission/restore paths before modifying shared APIs. Define a versioned provider extension for provider-scoped metadata and user-facing configuration, with size limits, provenance, unknown-field evolution and no provider-specific behavior in the shell.
2. Extend core catalog identity and user overlays: stable UUID, numeric compatibility alias, explicit ordering, visibility/grant policy, custom cover override and source-owned versus user-owned fields. Evolve provider artwork routing with opaque references, authenticated provider/source binding, content/type/size bounds and revision consistency. Preserve existing importer rows and reject cross-provider overwrites.
3. Carry authenticated client identity through a host-owned projection and enforce equivalent authorization for listing, artwork, direct UUID/numeric launch, resume and terminate; account for permission revocation, active owner, disconnect/resume and replacement. Keep effective client/app/global settings and launch metadata out of public list responses.
4. Exercise source synchronization on full/partial scans, revision change, interrupted batch, exclusions, expiration, uninstall/reinstall, duplicate cross-source games, manual edits and provider replacement. Verify failed/incomplete scans never delete records, and user's custom edits and covers survive permitted sync/restore.
5. Test UUID stability under rename, art change, reorder and restart; aliases, old clients, cached art refresh and stable ordered pagination; cover upload and invalid/oversize/mismatched data. Test per-client direct access denial and revocation, no disclosure from artwork, active owner retention and reconnect.
6. Qualify actual provider launch/focus/child ownership on target OS, prep partial failure and reverse undo, duplicate retries, cancellation during start, crash/restart, stale incarnations, stop failure and unconfirmed retirement. Keep source/tests, installed package, actual client streaming and native platform outcomes separately reported.
