# Pairing effect authority (integration checkpoint)

The optional `amaterasu.pairing-effects/1` service is **closed to production source binding**. Its current `bind` handler returns `source_attestation_unavailable` outside unit tests: NVHTTP has not yet joined its verified TLS peer to the lifecycle-issued source, and input/stream-session have not yet wired final effect and transport retirement. The ledger and a simulated pairing boundary test are not an end-to-end authorization proof. Do not enable an extension route based on this service yet. No installed permissions or settings are changed by this checkpoint.

The wire types and service name are in `amaterasu_module_sdk::effect_authority`. Test-only composition may select `effect_authority: { protocol_owner, effect_owner }` in pairing settings and must grant the exact service to those principals. The protocol owner must also be a configured pairing transport. Every request requires broker `caller == initiator`; `bind` is reserved for that protocol owner, `status` is available to either selected owner, and the remaining operations are reserved for the selected effect owner. No client chooses either principal. The PEM supplied on a future `bind` is visible only to the trusted protocol and pairing providers; it is never sent to the effect owner. Pairing checks the committed certificate and Launch permission and retains it privately. This code does not make native components a sandbox.

The lifecycle-derived source includes version, opaque source ID and generation, host epoch, opaque session and stream IDs, stream generation, device ID and device generation, and effect-owner boot epoch. All generations are nonzero, the source generation equals the stream generation, and the source is bounded. The protocol must prove that this tuple belongs to the authenticated connection before binding. That join is not yet implemented, and assertion by payload alone is insufficient.

The consumer contract is:

1. At startup, the authority reports `startup_recovery_required:true` and trust mutations wait. The selected effect owner asks `status {}` for the current authority `epoch`, retires any workers and transport from an older authority, then calls `recover {epoch, owner_epoch}`. Recovery rotates the epoch; if the reply is lost, `status` reveals the current epoch and owner epoch. A stale epoch cannot recover or admit. Restart recovery is a trusted owner assertion, not proof supplied by this SDK; the production worker must actually retire its previous incarnation.
2. After authenticating the lifecycle join, the selected protocol calls `bind {epoch, certificate_pem, source}`. The current checkpoint rejects this call in production.
3. The effect owner calls `admit {epoch, source, operation_id, sequence}` before dispatch. The strictly increasing, nonzero sequence is per authority epoch. An exact retry of a live operation returns the same ticket; changed source or sequence is rejected. The owner must deduplicate execution of an admitted operation. The ledger retains at most 256 operations; capacity exhaustion denies new admissions rather than expiring possibly active work.
4. The owner retains the ticket through the actual local effect or send and calls `complete {epoch, operation_id, ticket}` only after that worker is finished. `acknowledge` with the same fields frees a completed receipt; the high-water sequence prevents an old admission from being replayed. A lost admission reply is reconciled with `lookup {epoch, operation_id}`. A response with `fenced:true` is for retirement only; it does not authorize starting work.
5. Pairing synchronously fences new admissions before submitting a trust mutation. When any source was bound or work admitted, `status` reports `drain_required:true` and a `fence_generation`. Completion of tickets alone is insufficient: the effect owner stops admission and retires the relevant whole stream, ENet peer, retransmission and local queues, then sends `drain {epoch, fence_generation}` after all tickets complete. Pairing holds the state mutation until the matching drain is acknowledged. It cannot recall packets already sent on the network. The owner must poll status or use a future explicit notification; no notification channel is implemented here.

A provider failure, cancellation, missing ticket or lost drain acknowledgment must remain fenced until reconciled; elapsed time is not evidence of retirement. The current actor can service completion/status/drain requests while its mutation waits. It does not yet establish a lifecycle source binding or a production input/stream-session final-send handshake, and its unit tests do not establish live provider replacement or end-to-end behavior. In particular, restart/epoch safety still requires a tested worker-retirement handshake with the real effect owner. Hardware support and remote delivery are not implied.

A further opening condition is handling every identity invalidation path, including host-configuration refresh and provider failure, not only the pairing mutation branch. Admission rechecks the current pairing snapshot, so invalidation blocks new admissions, but this checkpoint does not coordinate a transport drain before every host-configuration identity transition. Keep source binding closed until those paths have equivalent retirement coverage and tests.

`amaterasu.session-lifecycle/1` now provides the read-only operation `resolve_effect_sources` to direct `amaterasu.nvhttp` with its coordinator-issued session `target`. It returns only currently active, non-revoked input bindings for that exact certificate-attested session, as `{status, target, sources:[{source:{version,id,generation}, target, input_consumer, input_boot_epoch}]}`. The response contains no input-binding token or certificate identity. NVHTTP must obtain the session target and certificate from its own authenticated launch record and must reject an input-supplied source that does not match this response; that NVHTTP bridge is not yet implemented. The response is a point-in-time observation, not effect admission. The pairing gate must be fenced on lifecycle stream retirement as well as pairing revocation before any route is enabled.

Pairing now fences the ledger whenever its identity snapshot is invalidated and refuses to republish identity until outstanding tickets and the owner drain have completed. A host-configuration update can commit before pairing observes it; this remaining pre-commit gap still requires a host-configuration-to-pairing fence handshake. Production binding remains disabled until that handshake, lifecycle retirement, and their integration tests are complete.

A configured authority that cannot initialize rejects trust mutations and fails module startup; it cannot fall back to ungated behavior. Delivered broker requests are checked for liveness before they mutate the gate or start a trust mutation. Cancellation after work actually starts still requires completion and drain.

## Stream-scoped feedback lease

The additive lease profile follows the orchestrator's explicit batching decision. A trusted protocol uses the additive `bind_stream` action with a `scope` containing the controller slot, an exact, nonempty negotiated capability set and the selected control transport's service, stream handle and provider epoch. Each capability is `{schema, version, direction:"to_client"}`, matching the input extension capability wire shape; the provider epoch is 32 lowercase hexadecimal characters. It is not client authority: the production protocol must authenticate both the source join and the negotiated capabilities before binding, and production binding remains closed. A scope cannot be changed on a bound source.

The selected effect owner requests `admit_stream_lease {epoch, source, operation_id, sequence, scope}`. Exactly one lease is allowed for the source/device generation in an authority epoch, even after completion and receipt acknowledgment. The successful admission returns the exact `source` and `scope`; the effect owner must compare them before using the lease. A retry must repeat the identical source, operation, sequence and scope. `lookup_stream_lease {epoch, source, operation_id, scope}` recovers a lost reply only for that exact scope; `fenced:true` is retirement-only. Ordinary `admit`, `lookup` and `complete` retain their one-shot behavior and cannot be used to complete a stream lease.

The owner may use that one previously admitted lease for sustained messages only while its local source queue is open. Pairing's fence denies new leases; the owner closes its local producer, retires the exact whole control stream and its ENet queues, then sends `complete_stream_lease {epoch, operation_id, ticket, retirement}`. `retirement` is an owner assertion of the authenticated transport's successful `whole_control_stream` / `retired` receipt, including the exact selected service, stream and provider epoch and the retirement operation ID. Pairing checks those fields against the original scope; JSON fields alone do not prove a broker receipt. After completing all tickets and leases the owner acknowledges the pairing drain as before. New messages inside an already admitted lease can finish while mutation waits; after drain acknowledgment, the owner must not hand off further data for the retired stream. Neither a lease nor a drain recalls an already handed-off packet or proves remote delivery.

The pairing ledger tests exercise 1,000 repeated observations of one lease, scoped replay rejection, retirement mismatch and fence ordering. They do not exercise 1,000 real audio blocks, an actual input owner, authenticated negotiation, transport replacement or final socket handoff. Those tests and independent review are required before production activation.
