# Client entitlement boundary

Vibepollo's `src/nvhttp.cpp` `getClipboard` and `setClipboard` each require a verified client, View, and a different client permission. Amaterasu's identity 1.1 fixed List/Launch/View selectors cannot express independent grants; a module's broker grant is a component authorization, not a remote-client permission. This contract enables distinct generic checks; it does not implement either operation, View, session ownership, protocol handling, or an effect fence.

Identity 1.2 appends a synchronous check to the selected identity provider. The trusted protocol owner maps each operation to a fixed entitlement from trusted composition, verifies TLS possession, and passes that connection's certificate and the exact name. Names have a lower-case ASCII reverse-DNS namespace with at least two segments, followed by `/` and an operation segment; segments allow letters, digits, hyphens and underscores. Maximum name length is 128 bytes. Trusted administrators allocate namespaces and approve the exact names and their meaning; plugins must coordinate ownership with administrators. There is no automatic ownership proof or registration: a module declaration never grants a client access. If two components use the same name they deliberately share the same policy; configuration must reject unintended collisions. Native plugins are trusted code, not sandboxed.

The pairing administrator can replace one client's bounded list using `update_client_entitlements`, certificate fingerprint, and `expected_revision`; only the existing administrator principal may write it. Empty/missing lists deny all, including when legacy permission mode is disabled. Existing permissions and old documents retain their behavior. Malformed names and duplicates are rejected. No name is implicitly approved or inherited. Unknown, unapproved, unpaired, expired, or unavailable authority never authorizes; every non-OK result denies. Bind minor 2 and full table size, and deny if unsupported. The input bytes are borrowed only for the call.

The authority reads a committed snapshot and verifies it remains current before returning. A policy mutation invalidates it while pending; subsequent checks see revocation after commit. A successful check is not a lease and cannot cancel or fence a concurrent effect. Consumers must recheck at appropriate effect and delivery boundaries and provide any stronger in-flight revocation, lifecycle and stream-ownership guarantees their operations need. The existing legacy permission checks remain separately required where applicable.
