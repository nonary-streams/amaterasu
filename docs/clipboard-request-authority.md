# Clipboard stream request authority checkpoint

This checkpoint is deliberately closed in normal builds. It adds a lifecycle stream reservation and pairing-side request accounting; it does not activate NVHTTP clipboard routing, prove a provider has retired, or implement host recovery.

`effect_authority::ClipboardStream` is `{version:1,host_epoch,session_id,stream_id,generation}`. Its fields identify one lifecycle stream; there is no controller, fabricated device or certificate in the value. The wire source is a selector, never a grant. Lifecycle accepts a reservation only for the direct protocol owner of a paired-attested session in the ready phase and an active stream of the exact generation. The selected protocol owner must obtain that source from the verified certificate-owned session and selected lifecycle provider, not from HTTP input.

Lifecycle requests, typed in `clipboard_authority::LifecycleRequest`, are `clipboard_stream_status`, `reserve_clipboard_stream`, `lookup_clipboard_stream`, `complete_clipboard_stream`, and `acknowledge_clipboard_stream`. Reserve contains `operation_id`, `source` and a strictly increasing nonzero sequence. Both authorities require `operation_id = source.operation_id(sequence)` from the SDK; the deterministic source-bound ID and highwater reject replay without accumulating a tombstone per completed copy. The lifecycle's persisted `clipboard_stream_status` returns the sequence highwater; success returns `{version:1,status:"reserved",operation_id,source,ticket}`. Retries of an identical live operation return its same ticket. Completion and acknowledgment require the same authenticated direct owner, operation and ticket. The status exposes the persisted sequence highwater; an unresolved operation after lifecycle restart reports `recovery_required` and blocks new clipboard admission. During stream quiescence the lifecycle target can no longer be reserved, and stream release waits for existing reservations to complete. Once acknowledged, its sequence and derived operation ID cannot be replayed in that lifecycle epoch.

Pairing's `AdmitClipboard` request contains the same stream, epoch, PEM from the internally authenticated TLS session, direction, operation ID and sequence. It checks the exact current paired certificate, View and the specific read/write grant before creating a bounded opaque ticket. `LookupClipboard`, `CompleteClipboard`, `AcknowledgeClipboard` and `FenceClipboardStream` retain/fence that ticket. Pairing's global trust or host-configuration fence denies new admissions and waits for in-flight clipboard tickets before allowing mutation. A stream-specific fence similarly denies new operations and reports pending until existing tickets settle. Pairing calls are restricted to the selected direct protocol owner; the selected stream owner may also request the stream fence. Pairing never returns certificate identity to a provider.

Correct ordering for the future NVHTTP adapter is: (1) use the TLS certificate to resolve the exact owned ready session and reserve an actually active stream at lifecycle; (2) obtain pairing's current direction permit for that same source; (3) dispatch the selected provider while holding both reservations; (4) finish a response only if the request remains authorized, and release reservations only once the actual provider and all locally queued response work have settled. If pairing admission is denied, settle the lifecycle reservation as no effect. A timed-out, canceled, abandoned or lost provider result is uncertain; it is not a completion receipt and neither reservation may be released merely on timeout. Reconcile by operation identity or retire and join the actual provider and its response queues. A write may already have committed: report uncertainty honestly and preserve the user's clipboard contents; retirement does not undo a completed write. Already admitted work can finish before a revocation commits; no new work may enter after the fence.

Important limitations: the selected NVHTTP path has not yet been wired to the lifecycle and pairing requests, and the pairing service does not independently query lifecycle before accepting the trusted protocol owner's stream assertion. The lifecycle and pairing admission methods are independently gated to tests. The existing provider contract in `f8f6db35` still uses a device-bound `Source` and must be changed by its owner to a stream-scoped source. Pairing restart also loses its volatile clipboard tickets; lifecycle's persisted uncertainty blocks new clipboard reservations, but a host-owned verified provider/owner retirement join is still needed before trust changes can safely proceed after a crash. Do not enable production until those paths are implemented and exercised together, including final-response, cancellation, disconnect and restart races.
