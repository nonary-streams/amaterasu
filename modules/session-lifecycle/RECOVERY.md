# Interrupted session end recovery

A coordinator restart fences the old epoch. It does not establish that capture,
input, application processes or provider resources have retired. A session owner
can resume a retained `end_session` that was still waiting for retirement and had
not dispatched any provider release.

Call `recover_session` through the existing lifecycle service using the same
authenticated caller and initiator that own the session:

```json
{
  "operation": "recover_session",
  "operation_id": "unique-recovery-attempt",
  "target": {
    "kind": "session",
    "host_epoch": "original-session-epoch",
    "session_id": "original-session-id",
    "generation": 1
  },
  "expected_host_epoch": "current-epoch-from-snapshot",
  "original_operation_id": "original-end-operation"
}
```

The original target, provider dependency graph, available retained method
contracts and every provider's frozen settings must match. Current setting
values do not replace the frozen values. Recovery rejects preparation work,
release work that reached a provider, unresolved actions or input, and child
streams without exact completed release evidence. It cannot create or resume a
stream in the old epoch.

For an unfinished external-capture child, the selected delegated capture
consumer first uses its existing `retire_stream` restart recovery operation
with actual native retirement evidence. That operation can adopt an untouched
child release generated by the session owner's `end_session`. The owner retries
session recovery only after every child completes. Unfinished managed capture
or input without independent retirement proof remains fenced.

For a bound application, recovery asks the installed launch service to verify
the frozen owner, launch ID and application operation ID. An unbound launch
requires the launch service's explicit `never_admitted` proof; absence or a new
epoch is insufficient. A desktop session with no launch uses its existing
explicit desktop retirement proof. Provider release remains behind this barrier.

A pending recovery receipt reports application verification. Lookup the original
end operation for final provider cleanup. A rejected verification leaves that
original operation recoverable with a fresh recovery operation ID. Another
coordinator restart requires a new `expected_host_epoch` and independent
verification. Successful proof supersedes only obsolete verification readbacks,
not effectful work. Completed receipts may later expire after their historical
checkpoint fences replay.

The callback-status recovery path is unchanged: its current-epoch session target
and retained provider receipt identify the original callback; it never replays an
unknown effect.

## Behavioral reference

Vibeshine `43cf27252a205221a295126a5fcd9ad87ba9c914` separates transport teardown
from application lifetime (`src/stream.cpp` stop/join and `src/process.cpp`
termination), holds resources while other borrowers drain, and retains native
restoration intent until the owning subsystem verifies completion. Its in-process
admission epoch barrier is not evidence of native retirement after a crash. This
implementation retains Amaterasu's independently authenticated provider proofs;
it does not adopt logical state clearing as retirement evidence.
