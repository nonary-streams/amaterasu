# Interrupted session end recovery

A coordinator restart fences the old epoch. It does not establish that capture,
input, application processes or provider resources have retired. A session owner
can resume a retained `end_session` that was still waiting for retirement and had
not dispatched any provider release.

Call `recover_session` through the existing lifecycle service using the same
authenticated caller and initiator that own the session:

```json
{
  "operation": "recover_session",
  "operation_id": "unique-recovery-attempt",
  "target": {
    "kind": "session",
    "host_epoch": "original-session-epoch",
    "session_id": "original-session-id",
    "generation": 1
  },
  "expected_host_epoch": "current-epoch-from-snapshot",
  "original_operation_id": "original-end-operation"
}
```

The original target, provider dependency graph, available retained method
contracts and every provider's frozen settings must match. Current setting
values do not replace the frozen values. Recovery rejects preparation work,
release work that reached a provider, unresolved actions or input, and child
streams without exact completed release evidence. It cannot create or resume a
stream in the old epoch.

For an unfinished external-capture child, the selected delegated capture
consumer first uses its existing `retire_stream` restart recovery operation
with actual native retirement evidence. That operation can adopt an untouched
child release generated by the session owner's `end_session`. The owner retries
session recovery only after every child completes. Unfinished managed capture
or input without independent retirement proof remains fenced.

Restarted stream retirement uses the same provider preflight as interrupted
session release. Before adopting release work or saving a new transition, it
checks the original stream dependency graph, frozen provider settings and
participant contracts against the installed selection. New snapshots freeze a
versioned SHA-256 identity of the complete installed participant contract before
effects; only settings values and their revision are excluded from that identity.
Changed plan,
callback or status methods, contract versions, cleanup methods, dependency shape
or capabilities reject recovery before provider dispatch. Current setting values
and revisions may change; release still uses the original frozen snapshots.
New code reads legacy snapshots without identity, but recovery requires an exact
retained prepare admission for every provider, bound to the same original epoch,
target and generation.
Another stream's admission or a release plan cannot substitute. Missing identity
and missing exact legacy evidence leave recovery fenced; malformed or unknown
identity versions also reject and cannot fall back to legacy evidence. Older
binaries that reject the new snapshot field cannot load a nonempty updated
journal; downgrading is not a recovery path.
Pending records must not be cleared to make an older binary load them.
This check adds no recovery effects and does not replace native retirement proof.

For a bound application, recovery asks the installed launch service to verify
the frozen owner, launch ID and application operation ID. An unbound launch
requires the launch service's explicit `never_admitted` proof; absence or a new
epoch is insufficient. A desktop session with no launch uses its existing
explicit desktop retirement proof. Provider release remains behind this barrier.

A pending recovery receipt reports application verification. Lookup the original
end operation for final provider cleanup. A rejected verification leaves that
original operation recoverable with a fresh recovery operation ID. Another
coordinator restart requires a new `expected_host_epoch` and independent
verification. Successful proof supersedes only obsolete verification readbacks,
not effectful work. Completed receipts may later expire after their historical
checkpoint fences replay.

The callback-status recovery path is unchanged: its current-epoch session target
and retained provider receipt identify the original callback; it never replays an
unknown effect.

## Input retirement bookkeeping

An input provider may attach a version 1 `retirement_receipt` to its existing
exact `retired` reply. The SDK binds this receipt to the input token, stream
target, revoke operation and provider boot epoch. The coordinator first saves
native retirement and the pending receipt in the same journal transaction, then
uses the public Input SDK's `acknowledge_binding_retirement` request. Only an
exact acknowledgement permits removing that stored receipt. The input provider
can then recycle the exact retired binding and idle context; this metadata
exchange cannot prove native cleanup or authorize input.

Pending acknowledgements survive coordinator restart. Result-release uncertainty
and failed journal writes retain the exact proof or acknowledgement for retry.
The combined live-binding and pending-acknowledgement budget is 128; unavailable
acknowledgement capacity stops new input admission rather than evicting history.
Malformed version 1 metadata fences its exact stream for recovery without
blocking unrelated retirement work. Providers that omit the optional receipt,
or advertise an unknown receipt version, keep their existing retirement protocol
and receive no acknowledgement request. New input providers remain compatible
with older consumers, which retain their old bounded-history behavior.

An empty pending book leaves the journal representation unchanged. A nonempty
`inputs.retirement_receipts` field requires this coordinator version; an older
strict reader may reject it. Do not discard these records to downgrade. This
change preserves restart ownership after the native proof transaction succeeds;
it does not recover a revoke operation whose identity was lost before that save.

## Behavioral reference

Vibeshine `43cf27252a205221a295126a5fcd9ad87ba9c914` separates transport teardown
from application lifetime (`src/stream.cpp` stop/join and `src/process.cpp`
termination), holds resources while other borrowers drain, and retains native
restoration intent until the owning subsystem verifies completion. Its in-process
admission epoch barrier is not evidence of native retirement after a crash. This
implementation retains Amaterasu's independently authenticated provider proofs;
it does not adopt logical state clearing as retirement evidence.
